## 0. 技术栈与项目总览

Finals Compass 是一个以"期末学习导航 + AI 解题与文档生成"为核心的教育平台，采用前后端分离 + 边缘协作的多进程架构。

| 层 | 技术 | 关键文件 |
| --- | --- | --- |
| 浏览器扩展 | Manifest V3、Service Worker、`chrome.scripting` | `browser-extension/{manifest.json,background.js,bridge.js}` |
| 前端 SPA | Vue 3.5.39、vue-router 5.2.0、Vite 8.1.4 | `apps/web/src/main.js`、`apps/web/src/App.vue`、`apps/web/src/api.js`、`apps/web/src/views/*.vue`、`apps/web/src/components/*.vue` |
| 前端关键依赖 | `dompurify ^3.4.13`、`marked ^18.0.9`、`katex ^0.18.1`、`pdfjs-dist ^6.1.200` | `package.json` |
| 后端 API | Spring Boot 3.5.3、Java 21、JDBC、Flyway、Redis、POI 5.4.1 | `services/api/pom.xml`、`services/api/src/main/resources/application.yml` |
| 文档解析 Worker | Python、FastAPI、MarkItDown、mutagen、pypdf | `services/markitdown-worker/app/{main.py,guards.py}` |
| 部署 | Docker Compose、Nginx、MySQL 8.0、Redis 7.4 | `deploy/{docker-compose.yml,nginx/finals-compass.conf,.env.example}` |

## 1. 前端架构总览

### 1.1 应用入口与路由（`apps/web/src/main.js`）

前端使用 Vue 3 的 Composition API + `createApp`，路由由 `vue-router` 的 `createWebHistory`（HTML5 History 模式）管理。`createApp(App).use(router).mount('#app')` 为唯一挂载点，无 Vuex/Pinia 等 centralized store——全局状态以**模块级 `ref` 单例**方式提供（见 1.3）。

路由表（`apps/web/src/main.js:16-28`）：

| 路径 | 组件 | 说明 |
| --- | --- | --- |
| `/` | `HomeView` | 课程导航首页 |
| `/cet` | `CetView` | 英语等级考试收录与做题 |
| `/ai-analysis` | （redirect）→ `/ai-center` | 旧路径迁移 |
| `/ai-center` | `AiCenterView` | AI Center 入口/路由决策 |
| `/ai-center/workflow` | `AiRuntimeChatView`（`meta.runtime='WORKFLOW'`） | Workflow 运行时对话 |
| `/ai-center/agent` | `AiRuntimeChatView`（`meta.runtime='AGENT'`） | Agent 运行时对话 |
| `/ai-center/web-agent` | `AiRuntimeChatView`（`meta.runtime='MULTI_WEB_AGENT'`） | 多 WebAgent 协作对话 |
| `/ai-center/vcp` | `VcpRuntimeView` | VCP 运行时视图 |
| `/courses/:courseId` | `TeachersView` | 课程下的任课老师列表 |
| `/courses/:courseId/teachers/:teacherId` | `TeacherCircleView` | 老师圈（资料/讨论/指南） |

> **设计观察（已核实）**：`AgentRuntimeView.vue`、`WorkflowRuntimeView.vue`、`WebAgentRuntimeView.vue` 三个视图文件虽存在于 `apps/web/src/views/`，但**对 `apps/web/src/` 全量检索未发现任何 `import` 引用**（`main.js` 路由亦未声明）——`/ai-center/{workflow,agent,web-agent}` 统一渲染 `AiRuntimeChatView` 并以 `route.meta.runtime` 区分模式。按文件内容看，它们疑似将三种运行时统一重构进 `AiRuntimeChatView` 后遗留的旧实现（`WorkflowRuntimeView` 内仍保留 `documentApi.plan/outline/style` 调用代码），属当前未被挂载的孤立文件，可考虑清理确认。`scrollBehavior: () => ({ top: 0 })` 保证路由切换回到顶部。

### 1.2 应用外壳与认证门控（`apps/web/src/App.vue`）

`App.vue` 是整个 SPA 的外壳，承担三类职责：

1. **首屏过渡**：`introVisible` 控制一张随机背景图（`import.meta.glob('../pictures/*.{jpg,jpeg,png,webp}')`，`apps/web/src/App.vue:56-58`）的进入动画，点击/回车后经 `transitionScene`（tree/waves/vine 三选一）淡出。
2. **认证门控**：
   - `introVisible` 为假且 `!authenticated` → 渲染 `AuthView`（登录/注册/Beta 申请）。
   - `authenticated` 为真 → 渲染 `app-shell`（顶栏 + `<router-view/>` + `<SuspendRest/>`）。
   - 认证状态来自 `api.js` 导出的 `authenticated` computed（基于服务端恢复的用户名）。
3. **全局功能抽屉/模态**：顶栏账户菜单按 `isAdmin`（`role === 'ADMIN'`）条件性暴露管理员入口：内容审核、登录验证（Beta 发放）、SMTP 与邮件、MCP 管理中心、AI Skill 优化、公告管理、暂挂体验管理、调查问卷管理。这些弹窗以独立组件挂载（`AdminSuspendModal`、`AdminMailModal`、`AdminMcpModal`、`AdminAiFeedbackModal`、`AdminSurveyModal`/`UserSurveyModal`），由 `showXxx` 布尔 ref 驱动。

其他外壳能力：主题切换（`system/light/dark` 三态循环，写入 `localStorage['finals-compass-theme']` 并设 `document.documentElement.dataset.theme`，监听 `prefers-color-scheme`）、`Escape` 关闭所有浮层、公告在登录身份变化时自动加载、强制改密（`mustChangePassword` 为真时自动弹出改密框且不可点击遮罩关闭）。

### 1.3 状态管理：无 centralized store 的响应式单例

项目**未使用 Pinia/Vuex**。跨组件共享状态集中在 `apps/web/src/api.js` 顶部的模块级响应式变量：

- `authSession = ref({ username, displayName, role, mustChangePassword })`：服务端恢复的公开会话资料（不含令牌）。
- `authenticated = computed(...)`、`isAdmin = computed(...)`：派生态。
- `profile = ref({ publicId, nickname })`：匿名身份。

这些 `ref`/`computed` 在 `App.vue` 与各视图间通过 `import` 直接共享，Vue 的响应式系统保证变更广播。令牌仅存在 HttpOnly Cookie 中，刷新时由 `GET /api/auth/session` 恢复公开资料；前端 JavaScript 无法读取会话令牌。

### 1.4 API 客户端设计（`apps/web/src/api.js`）

`apps/web/src/api.js` 是唯一的 HTTP 层，所有视图通过它访问后端。核心是两个内部函数与一组按业务领域分组的 API 对象。

**通用请求**：

- `request(path, options)`（`apps/web/src/api.js:14-29`）：
  - 使用 `credentials: include` 携带 HttpOnly 会话 Cookie，写请求自动注入双提交 `X-CSRF-Token`。
  - 失败时解析 JSON 错误体，读取响应头 `X-Trace-Id` 并拼入错误消息（便于后端追踪）。
  - `401`（非 `/auth/login`）触发 `clearSession()`，实现 token 失效自动登出。
  - `204` 或 `content-length: 0` 返回 `null`，否则返回 JSON。
- `requestBlob(path)`（`apps/web/src/api.js:31-42`）：用于文件下载（资料、CET 音频、文档产物），返回 `Blob`。

**按领域分组的 API 对象**（每个方法对应一个后端端点，是理解前端能力清单的权威来源）：

| 对象 | 覆盖能力 | 代表端点 |
| --- | --- | --- |
| `authApi` | Beta 申请/验证、登录、注册、改密、登出 | `/auth/beta-access/{request,verify}`、`/auth/{login,register,change-password,logout}` |
| `initIdentity()` | 取得/刷新匿名身份 | `/identity/anonymous` |
| `catalogApi` | 课程/学院/老师基础数据 | `/courses`、`/courses/colleges`、`/courses/:c/teachers` |
| `circleApi` | 老师圈资料、讨论、指南、上传、感谢、文件下载 | `/circles/:c/:t/{resources,discussions,guide}` |
| `systemApi` | 公告、Beta 审批、SMTP/Microsoft 邮件、模板、审核、指标 | `/system/{announcement,mail/*,moderation,metrics,...}` |
| `mcpAdminApi` | MCP 服务器配置/发现/OAuth/审批 | `/system/mcp/servers/...`、`/system/mcp/approvals` |
| `surveyApi` | 问卷题目与提交 | `/survey`、`/survey/admin` |
| `aiApi` | AI 仪表盘、BYOK/平台 Key、解题调用、附件转换 | `/ai/{dashboard,byok,invoke,attachments/convert}` |
| `documentApi` | 文档模板/规划/大纲/样式/产物下载 | `/ai-center/documents/{templates,plan,jobs/:k,artifacts/:id}` |
| `aiCenterApi` | 运行时列表、路由决策、内容、任务、调度 | `/ai-center/{runtimes,route,content,runtime/tasks,dispatch}` |
| `aiFeedbackApi` | 反馈邀请/提交/忽略、优化队列审批 | `/ai-center/feedback*`、`/system/ai-feedback/optimization` |
| `aiEvolutionApi` | AI 进化仪表盘/刷新/建议复核 | `/system/ai-evolution*` |
| `skillWorkbenchApi` | Skill 版本工作台（创建/草稿/用例/评测/发布/回滚） | `/system/ai-skill-workbench/*` |
| `cetApi` | CET 试卷/题目/音频 | `/cet/{papers,items,audio}`、`/auth/stream-cookie` |

`API_BASE` 来自 `import.meta.env.VITE_API_BASE || '/api'`，开发期由 `vite.config.js` 的 `server.proxy['/api']` 转发到 `http://localhost:8080`（后端）。生产期由 Nginx 代理（见 7.2）。

> **设计观察**：`request()` 统一注入 `X-Trace-Id` 读取与 401 处理，意味着后端 `RequestTraceFilter`（见后端文档）的追踪号能一路透传到用户可见的错误提示，是一种可观测性友好的设计。

### 1.5 主题与可访问性

主题三态（system/light/dark）循环切换，CSS 通过 `[data-theme]` 选择器适配。首屏过渡图、按钮均带 `aria-label`/`role`，模态带 `role="dialog" aria-modal="true"`。`closeOverlays` 用键盘 `Escape` 统一收起浮层。

## 2. 视图（Views）逐项说明

> 视图的"职责"主要依据其调用的 API 分组与路由元信息推断，结合文件命名约定。

### 2.1 `HomeView.vue`（`/`，课程导航）

平台首页。展示课程/学院导航，调用 `catalogApi.courses()`/`colleges()`，进入具体课程后跳转 `/courses/:courseId`（`TeachersView`）。承担"入口大厅"角色。

### 2.2 `AuthView.vue`（未认证外壳内渲染）

登录/注册/Beta 申请一体化视图。由 `App.vue` 在 `!authenticated` 时渲染，并接收 `:scene` 用于过渡动画（`AuthTransitionScene` 组件提供 tree/waves/vine 三种场景）。调用 `authApi.requestBetaAccess/verifyBetaAccess/login/register`。登录成功后 `api.js` 自动调用 `initIdentity()` 取得匿名身份。

### 2.3 `CetView.vue`（`/cet`，英语等级考试）

CET 试卷与题目管理/做题视图。调用 `cetApi.papers/items/createPaper/...`、`cetApi.audio/prepareAudioStream/audioUrl`。音频播放走"流式 Cookie"模式：先 `POST /auth/stream-cookie` 取得一次性 Cookie，再用 `<audio src="/api/cet/items/:id/audio">` 播放，避免把 Bearer token 放进媒体 URL。

### 2.4 `AiCenterView.vue`（`/ai-center`，AI Center 入口）

AI Center 总入口。调用 `aiCenterApi.runtimes()` 列出可用运行时、`aiCenterApi.route(goal, preferredRuntime, clientCapabilities)` 让后端决策把目标路由到 WORKFLOW / AGENT / MULTI_WEB_AGENT / VCP 等运行时，再跳转到对应子路由。还管理 AI Center 内容页（`aiCenterApi.content/updateContent`）。

### 2.5 `AiRuntimeChatView.vue`（`/ai-center/{workflow,agent,web-agent}`）

AI Center 最核心的 AI 交互视图，一份组件服务三种模式，靠 `route.meta.runtime` 区分（`modes` 映射名称与提示语）：

- **WORKFLOW**：调用 `aiCenterApi.workflowTask({input, credentialSource, provider, model, ephemeralApiKey, modalities})` 提交工作流任务，返回 `outputJson` 经 `readable()` 解析后展示，附 `taskId` 作 trace。文档生成的 plan/outline/style/artifact 流程也在此模式下驱动（见 7.4）。
- **AGENT**：要求 `extensionConnected`（Chrome 扩展在线），先 `window.postMessage(START_AGENT_BROWSER)` 让扩展做 Bing 检索+网页抽取，拿到 `AGENT_BROWSER_RESULT` 拼成 `agentGoal`，再调 `aiCenterApi.dispatch({runtimeType:'AGENT'})`。
- **MULTI_WEB_AGENT**：要求扩展，调 `aiCenterApi.dispatch({runtimeType:'MULTI_WEB_AGENT', providers:['KIMI','DEEPSEEK','QWEN']})` 取 `runKey`，再 `postMessage(START_RUN)` 让扩展打开三家网页 AI 标签页并行提问。

通用能力：附件最多 3 个、单文件 ≤20MB，`convert()` 调 `aiApi.convertAttachment` 转 Markdown 后拼进 goal；监听 `extensionMessage` 处理扩展回传的 `READY`/`AGENT_BROWSER_RESULT`/`PARTICIPANT_STATUS`，后者经 `aiCenterApi.reportParticipant` 回传后端聚合；凭据来源 `settings.credentialSource`（PLATFORM/STORED_BYOK/EPHEMERAL_BYOK，EPHEMERAL 用完即清）；助手消息用 `defineAsyncComponent(SafeMarkdown)` 渲染。这是浏览器扩展（WebAgent 桥）在前端的对端。

### 2.6 `VcpRuntimeView.vue`（`/ai-center/vcp`）

VCP（疑似"视觉/拍题"类）运行时视图。配合 `aiApi.invoke` 的"临时拍题"链路（详见 `FinalsCompass_AI_V3_真实调用与临时拍题设计.md`、`FinalsCompass_AI_V4_Gemini视觉与DeepSeek解题编排.md`）。

### 2.7 `TeachersView.vue`（`/courses/:courseId`）

某课程下的任课老师列表，调用 `catalogApi.teachers(course)`。

### 2.8 `TeacherCircleView.vue`（`/courses/:courseId/teachers/:teacherId`）

"老师圈"——围绕某位老师的资料、讨论、学习指南。调用 `circleApi.resources/discussions/guide/updateGuide/submitGuideReference/thank/upload/file`，是 UGC 与审核的核心界面（提交内容经后端审核后才公开，见 `systemApi.moderation`）。

### 2.9 孤立视图文件（未被挂载）

`apps/web/src/views/` 下还存在 `AgentRuntimeView.vue`、`WorkflowRuntimeView.vue`、`WebAgentRuntimeView.vue` 三个文件，但**对 `apps/web/src/` 全量检索未发现任何 `import` 引用**（`main.js` 路由亦未声明），当前不会被渲染。按文件内容看，它们疑似将 Agent/Workflow/WebAgent 三种运行时统一重构进 `AiRuntimeChatView`（以 `meta.runtime` 区分）之前的旧实现：

- `AgentRuntimeView.vue`：Agent Runtime 介绍页，展示四阶段架构（Goal Understanding→Task Planning→Governed Execution→Self Review）与 Agent Gateway 接入状态。
- `WorkflowRuntimeView.vue`：保留文档生成三阶段流程（`documentApi.plan`/`outline`/`style`/`artifact`）的旧实现，疑似已被 `AiRuntimeChatView` 的 WORKFLOW 模式取代。

## 3. 组件（Components）逐项说明

组件分两类：**全局挂载组件**（在 `App.vue` 模板中直接条件渲染）与**视图内组件**（由具体视图引用）。

### 3.1 渲染类组件（安全关键）

这三个组件是前端"不可信内容渲染"的统一收口，是 XSS 防御的基石：

- **`SafeHtml.vue`**：极简单文件组件。`computed` 对 `props.content` 调 `DOMPurify.sanitize(content, {USE_PROFILES:{html:true}, ADD_ATTR:['target','rel']})` 后 `v-html` 输出。`ADD_ATTR` 允许 `target`/`rel` 以支持外链新窗口打开。用于 VCP 介绍页与 AI Center 内容管理。
- **`SafeMarkdown.vue`**：三层渲染管道 `marked` + KaTeX + DOMPurify：(1) `renderMathOutsideCode(source)` 用正则按代码块分段，**代码块内不处理公式**，其余段做四种公式替换（`$$…$$`、`\[…\]`、`\(…\)`、`$…$`）分别调 `katex.renderToString`（`throwOnError:false, trust:false, output:'html'`）；(2) `marked.parse(...)`（`gfm:true, breaks:true`）转 HTML；(3) `DOMPurify.sanitize(..., {USE_PROFILES:{html:true, svg:true, mathMl:true}})` 净化后 `v-html` 输出。注释说明 `output:'html'`（而非 MathML+HTML）是为避免复制时产生重复公式文本。
- **`PdfViewer.vue`**：基于 `pdfjs-dist`（用 `legacy/build/pdf.mjs` 兼容旧移动浏览器）。Worker 经 `?url` 导入并设 `GlobalWorkerOptions.workerSrc`。`renderPdf(blob)`：`getDocument` 携带 `cMapUrl`/`standardFontDataUrl`/`wasmUrl`（指向 `/pdfjs/` 静态资源）+ `useSystemFonts`，逐页 `getPage`→`getViewport({scale:1.35})`→按 `devicePixelRatio`（上限 2）创建 canvas→`render`→`page.cleanup()`；解析失败回退 `nativeMode`（`<iframe>` 用 `blob:` URL 直接渲染）；`onUnmounted` 销毁 task/documentHandle 并 revoke URL。`apps/web/public/pdfjs/` 下携带标准字体（Foxit/Liberation）、cmaps（中日韩字符映射）、wasm（JBIG2/OpenJPEG/QuickJS/QCMS，用于扫描件/图像解码）。

> **设计要点**：把净化能力收敛为 `SafeHtml`/`SafeMarkdown` 两个专用组件，是一种"默认安全"的架构约束——开发者只要使用这两个组件渲染不可信内容，就自动获得 XSS 防护。安全风险在于是否有视图绕过它们直接用 `v-html`（详见安全审计报告）。

### 3.2 全局模态/抽屉组件（`App.vue` 挂载）

| --- | --- | --- |
| `AuthView.vue` | `!authenticated` | 登录/注册/Beta（见 2.2） |
| `AuthTransitionScene.vue` | `App.vue` 传 `:scene` | 登录页过渡场景动画（tree/waves/vine） |
| `SuspendRest.vue` | 始终挂载于 `app-shell` | 全局"暂挂体验"入口（详见 `暂挂体验模块设计与维护.md`） |

## 4. 浏览器扩展架构（`browser-extension/`）

扩展名为 **"Finals Compass AI Runtime Bridge"**（MV3），是"多 WebAgent 协作"运行时的边缘执行器：它代替用户在多个第三方 AI 聊天网站（Kimi、DeepSeek、千问）中自动提问并收集答案，或通过 Bing 搜索+网页抽取做"Agent 浏览器研究"。

### 4.1 manifest 与权限模型（`manifest.json`）

- `manifest_version: 3`，`background` 为模块化 Service Worker（`background.js`）。
- `permissions`: `["tabs","scripting","storage"]`——开标签页、注入脚本、本地存储状态。
- `host_permissions`：明确列出 `localhost:5173`、`127.0.0.1:5173`、Kimi/DeepSeek/千问/通义/Bing/Google，**并以 `https://*/*` 兜底**（所有 HTTPS 站点）。后者是为"Agent 浏览器研究"能跟随任意搜索结果页。
- `content_scripts`：`bridge.js` 仅注入到 `localhost:5173` / `127.0.0.1:5173`，`run_at: document_start`——确保在主站脚本之前建立消息桥。
- `action.default_popup`: `popup.html`。

> **设计观察（安全相关）**：`https://*/*` 是极宽的 host 权限，意味着扩展理论上可在任意 HTTPS 站点注入脚本。当前 `content_scripts` 只匹配本地主站，但 `scripting` 权限配合宽 host 权限仍是一个需要审慎对待的攻击面（详见安全审计报告）。

### 4.2 `background.js`：多 Provider 编排与 Agent 浏览器研究

Service Worker 监听两类消息（`background.js:10-13`）：

1. **`START_RUN` → `run()`**（多 Provider 并行执行）：
   - `run()`（`:46-49`）对每个 `participants`（默认全部 `PROVIDERS`）并发调用 `execute()`。
   - `execute(runKey, goal, providerKey, appTabId)`（`:51-63`）：开一个后台标签页打开 Provider URL → `waitLoaded`（最多 60×500ms 轮询）→ `chrome.scripting.executeScript` 注入 `inspectAndSubmit`，在编辑器（`textarea`/`[contenteditable]`/`.ql-editor`/`.ProseMirror`）里填入 prompt 并点发送键 → 返回 `RUNNING`/`LOGIN_REQUIRED`/`FAILED`。
   - `pollAnswer(tabId, before)`（`:73-89`）：120 次 ×1.5s 轮询，连续 4 次答案稳定即返回 `COMPLETED`，否则 `RESPONSE_TIMEOUT`。
   - `notify(appTabId, payload)`（`:91-94`）：通过 `chrome.tabs.sendMessage` 回传给发起标签页的 `bridge.js`，并存 `chrome.storage.local.lastStatus`。
   - `LOGIN_REQUIRED` 时把该标签页 `active` 拉到前台，提示用户登录。
2. **`START_AGENT_BROWSER` → `agentResearch()`**（`:15-29`）：
   - 开后台标签页 `https://www.bing.com/search?q=<goal>` → `collectSearchResults` 抓前 6 条结果 → 取前 3 条逐个打开 → `extractReadablePage` 抽取正文（去 script/style/nav 等，`innerText` 截断 16000 字符）→ 关闭标签页 → 回传 `{requestId, status:'COMPLETED', result:{query, pages}}`。

`PROVIDERS`（`:1-5`）配置了 Kimi/DeepSeek/千问 的 URL 与各自 `roles`（角色提示，如"请独立分析，重点检查逻辑、事实和遗漏"），构成一个"多模型互检"编排。

### 4.3 `bridge.js`：postMessage 桥接协议

`bridge.js` 是注入到主站的内容脚本，负责"主站 ↔ 扩展"消息双向转发（`bridge.js:1-21`）：

- **来源标识**：扩展发出用 `source: 'FINALS_COMPASS_WEBAGENT_EXTENSION'`，只接受 `source: 'FINALS_COMPASS_WEBAPP'` 的主站消息（`event.source === window` 校验防止跨域冒充）。
- **握手**：加载即 `emit('READY')`；主站发 `PING` 则回 `READY`。
- **下行（主站→扩展）**：`START_RUN`（带 `runKey/goal/participants`）、`START_AGENT_BROWSER`（带 `requestId/goal`）→ `chrome.runtime.sendMessage` 转给 background。
- **上行（扩展→主站）**：background 回传的 `PARTICIPANT_STATUS` / `AGENT_BROWSER_RESULT` → `emit(...)` 广播 `window.postMessage`，主站的 `AiRuntimeChatView`（MULTI_WEB_AGENT 模式）监听并更新 UI。

> **设计观察**：`bridge.js` 用 `event.source === window` + 固定 `source` 字符串做来源校验，是 postMessage 跨窗口通信的常见轻量防御；但 `emit(...}, '*')` 的 `targetOrigin` 为通配，理论上任意同源页可收到广播（详见安全审计报告）。

### 4.4 与主站 WebAgent 的协作流程

`MULTI_WEB_AGENT` 运行时下，主站 `AiRuntimeChatView` 经 `aiCenterApi.dispatch` 启动一次 dispatch run，随后通过 `window.postMessage(START_RUN/START_AGENT_BROWSER)` 驱动扩展；扩展在第三方站点执行后把 `PARTICIPANT_STATUS`/`AGENT_BROWSER_RESULT` 回传，主站再经 `aiCenterApi.reportParticipant` 上报后端，由后端 `AiCenterRuntimeService`/`AiRuntimeRouterService` 汇总多 Agent 结果。

## 5. MarkItDown Worker 架构（`services/markitdown-worker/`）

一个独立的 Python 微服务，把用户上传的附件（PDF/Office/图片/音频/文本）统一转成 Markdown，供 AI 链路作为上下文。后端 `AiDocumentConversionService` 通过 `MARKITDOWN_WORKER_URL` + `MARKITDOWN_WORKER_TOKEN` 调用它。

### 5.1 部署形态

在 `docker-compose.yml` 中作为独立服务 `markitdown-worker`（端口 8090，仅 `app-network` 内部可达，不发布宿主端口），关键加固（`deploy/docker-compose.yml:72-94`）：

- `read_only: true`（根文件系统只读）。
- `tmpfs: /tmp:size=256m,mode=1777`（临时目录单独可写）。
- `security_opt: no-new-privileges:true`。
- 资源限额全量走环境变量：`MAX_BYTES`(20MB)、`MAX_CHARS`(60000)、`MAX_CONCURRENCY`(2)、`MAX_PDF_PAGES`(80)、`MAX_AUDIO_SECONDS`(600)、`MAX_ARCHIVE_ENTRIES`(2000)、`MAX_UNPACKED_BYTES`(100MB)、`MAX_COMPRESSION_RATIO`(200)。

### 5.2 `/convert` 端点与处理管道（`app/main.py`）

`FastAPI` 应用关闭了 docs/redoc（`docs_url=None`）。唯一业务端点 `POST /convert`（`main.py:48-101`）：

1. **鉴权**：`authorize(x_worker_token)`（`:36-40`）——`MARKITDOWN_WORKER_TOKEN` 必须配置且用 `hmac.compare_digest` 常量时间比较，拒绝则 401/503。
2. **取扩展名**：`Path(file.filename).name`（`.name` 取 basename，防 `../` 路径穿越）。
3. **白名单**：`ALLOWED_EXTENSIONS` 仅放行 pdf/docx/pptx/xls/xlsx/txt/md/csv/json/xml/html/htm/png/jpg/jpeg/webp/wav/mp3/m4a。
4. **大小**：`file.read(MAX_BYTES+1)`，超限 413。
5. **多层校验**（见 5.3）：`validate_signature` → `validate_archive` →（pdf）`validate_pdf` →（音频）`validate_audio`。
6. **转换**：`tempfile.TemporaryDirectory` 内写 `input<ext>` → 经 `asyncio.Semaphore` 限并发 → `asyncio.to_thread(convert_local, path)` 调 `MarkItDown(enable_plugins=False).convert_local(path)`。
7. **截断**：Markdown 超 `MAX_CHARS` 截断并标记 `truncated`。
8. **返回**：`{fileName, contentType, markdown, characters, truncated}`。

> **设计要点**：`enable_plugins=False` 关闭 MarkItDown 插件，缩小攻击面；converter 实例 request-scoped（注释说明第三方解析器不保证线程安全）；转换失败统一 422，不泄露内部异常细节。

### 5.3 `guards.py`：多层内容校验

`guards.py` 在字节进入解析器之前做"签名/结构/资源"校验，把恶意构造挡在解析器外：

- **`validate_signature`**（`:21-47`）：按扩展名校验魔数（PDF `%PDF-`、Office `PK\x03\x04`、legacy Excel OLE、PNG/JPEG/WebP/WAV/MP3/M4A），文本类还要求无 `\x00` 且 UTF-8 可解码。防止"扩展名欺骗"。
- **`validate_archive`**（`:50-76`）：对 Office（zip）做 zip-bomb 防御——条目数上限、累计解压大小上限、单条压缩比上限、拒绝加密归档（`flag_bits & 0x1`）、校验预期根目录（`word/`、`ppt/`、`xl/`）与 `[Content_Types].xml` 存在。
- **`validate_pdf`**（`:79-89`）：拒绝加密 PDF、页数上限。
- **`validate_audio`**（`:92-101`）：用 `mutagen` 读时长，拒绝无法判定时长或超时长音频。

> 这套校验是"纵深防御"的范例：即使底层 MarkItDown/POI/pypdf 等解析器存在未知漏洞，恶意构造在到达它们之前已被签名与结构校验拦截。

## 6. 部署架构（`deploy/`）

### 6.1 docker-compose 服务拓扑（`deploy/docker-compose.yml`）

五个服务，统一 `app-network`（bridge 驱动）：

```
            ┌──────────────┐
   :80 ───▶ │   frontend   │ (nginx, profile=container-frontend, 可选)
            └──────┬───────┘
                   │ /api/ 代理
            ┌──────▼───────┐
 :8080(127)│   backend    │ depends_on: mysql, redis, markitdown-worker
            └──┬──┬──┬─────┘
               │  │  │
   ┌───────────┘  │  └──────────────┐
   ▼              ▼                 ▼
 mysql          redis          markitdown-worker
 (mysql_data)  (requirepass    (read_only+tmpfs,
                +no-new-priv)   :8090 内部)
```

| 服务 | 镜像/构建 | 端口 | 加固/约束 |
| --- | --- | --- | --- |
| `mysql` | `mysql:8.0` | 不发布 | `env_file: .env`；数据卷 `mysql_data` |
| `backend` | `deploy/services/api/Dockerfile` | `127.0.0.1:8080:8080` | `JAVA_TOOL_OPTIONS` 内存上限；`UPLOAD_DIR=/app/uploads`；环境变量注入全部密钥 |
| `redis` | `redis:7.4-alpine` | 不发布 | `--requirepass` + `--maxmemory 256mb --maxmemory-policy noeviction` + `no-new-privileges` |
| `markitdown-worker` | `services/markitdown-worker/Dockerfile` | 不发布（内部 8090） | 见 5.1 |
| `frontend` | `deploy/frontend/Dockerfile` | `80:80` | `profiles: container-frontend`（可选，默认不启动，常以 Nginx 直连后端） |

数据卷：`mysql_data`、`uploads`（后端上传目录跨重建持久化）。

> **设计观察**：MySQL 与 Redis 均**不向宿主发布端口**，只在 `app-network` 内部可达，减小外部攻击面。后端端口绑定 `127.0.0.1:8080`，避免直接公网暴露。但后端 DB URL 含 `allowPublicKeyRetrieval=true&useSSL=false`（容器间内网通信的常见取舍），详见安全审计报告。

### 6.2 Nginx 路由（`deploy/nginx/finals-compass.conf`）

监听 `:80`（`default_server`），`server_name _`（兜底）。三条 location：

1. `= /api/ai/invoke`（`:12-21`）：精确匹配 AI 解题端点，`proxy_request_buffering off`——摄像头拍题的请求体**直通后端**，避免 Nginx 把大 body 落盘到 `client_body_temp`（注释明确说明这是 request-scoped 相机图像的优化）。`proxy_read_timeout 120s`。
2. `/api/`（`:23-31`）：其余 API 代理到 `backend:8080`，转发 `Host/X-Real-IP/X-Forwarded-For/X-Forwarded-Proto`。
3. `/`（`:33-35`）：`try_files $uri $uri/ /index.html`——SPA History 路由的 fallback。

静态资源：`.mjs` 单独设 `application/javascript` MIME（Ubuntu 默认 `mime.types` 可能缺，避免 ES module worker 失败）+ 7 天缓存 `immutable`；css/js/图片/字体同样 7 天缓存。

> **设计观察**：Nginx 配置当前仅 HTTP（`:80`），未配置 TLS/HSTS，也缺少 `X-Frame-Options`/`Content-Security-Policy`/`X-Content-Type-Options` 等安全头与 `server_tokens off`——TLS 终结通常在前置 LB/CDN，但安全头缺失值得记录（详见安全审计报告）。

### 6.3 Dockerfile 构建链

- `deploy/frontend/Dockerfile`：Vite 构建产物 → Nginx 镜像。

```

```

### 7.4 文档生成（三阶段确认式 DAG）

文档生成走"plan→outline→style→artifact"的三阶段确认式流程（由 AI Center 的 Workflow 模式视图驱动）：

```
① plan 阶段
  documentApi.plan({goal, format, style, templateKey, credentialSource, ...})
  --POST /ai-center/documents/plan-->
    DocumentGenerationController.plan → DocumentPlanningService.plan
      → AiInputGuardrail → AiCredentialResolver → AiUsageGuardService.check
      → 调 Planning Skill（LLM 生成 Blueprint：title/subject/sections[].bullets）
      → DocumentBlueprintValidator 校验 format 一致
      → DocumentGenerationService.submit → 落库 document_job（status=OUTLINE_PENDING）
      → RuntimeExecutionTraceStore 记录
  <-- {jobKey, status:OUTLINE_PENDING, blueprint}   前端展示可编辑框架

② outline 阶段（可改后重跑或确认）
  documentApi.outline(jobKey, {approved, feedback, revisedBlueprint})
  --POST /ai-center/documents/jobs/:key/outline-->
    approved=false → 带 feedback 重跑 Planning Skill（仍 OUTLINE_PENDING）
    approved=true  → 生成 PREVIEW artifact（前 2 章节）→ status=STYLE_PREVIEW_PENDING

③ style 阶段
  documentApi.style(jobKey, {approved, feedback, templateKey})
  --POST /ai-center/documents/jobs/:key/style-->
    approved=false → 换模板重生 PREVIEW
    approved=true  → DocumentGeneratorRegistry 生成 FINAL artifact（PDF/PPTX/DOCX/XLSX/HTML）
                    HtmlDocumentGenerator / PlaywrightPdfDocumentGenerator / PoiDocx/Pptx/Xlsx
                  → DocumentArtifactStorage 持久化 → status=COMPLETED
  视图 --GET /ai-center/documents/artifacts/:id (requestBlob)--> Blob 下载
  COMPLETED → aiFeedbackApi.offer({documentJobKey, triggerType:FILE_GENERATION}) 触发反馈
```

`DocumentGenerationService` 注入 `JdbcClient`/`ObjectMapper`/`DocumentBlueprintValidator`/`DocumentGeneratorRegistry`/`DocumentArtifactStorage`；`DocumentPlanningService` 额外注入 `AiProviderGateway`/`AiCredentialResolver`/`AiUsageGuardService`/trace store。Workflow DAG 执行时 `RuntimeDocumentWorkflowNodeHandler` 复用 `submit/confirmOutline/confirmStyle`，使文档节点可嵌入 Workflow 编排。

## 9. 设计要点小结

1. **无 centralized store 的响应式单例**：全局状态是 `api.js` 模块级 `ref`，简洁但要求开发者自律（token 存 localStorage 的 XSS 权衡）。
2. **统一 API 客户端**：`request()` 收口鉴权头注入、401 自动登出、`X-Trace-Id` 透传、错误归一，所有视图共用，可观测性好。
3. **默认安全的渲染收口**：`SafeHtml`/`SafeMarkdown` 把 DOMPurify 净化收敛为专用组件，降低 XSS 暴露面。
4. **边缘协作运行时**：浏览器扩展作为"多 WebAgent 协作"的执行器，通过 postMessage 桥与主站联动，是少见的"用真实第三方 AI 网站做并行研究"的设计。
5. **纵深防御的 Worker**：MarkItDown Worker 在 read-only 容器内，以"签名→结构→资源→解析"多层 guard 把恶意附件挡在解析器前。
6. **内网收敛的部署**：MySQL/Redis/Worker 均不发布宿主端口，后端绑 `127.0.0.1`，敏感配置全走环境变量与 `.env`（且 `.env` 被 git 忽略）。
7. **可观测的追踪号**：`RequestTraceFilter` 产出的 `X-Trace-Id` 一路透传到前端错误提示，便于跨端排障。
8. **孤立视图文件**：`AgentRuntimeView`/`WorkflowRuntimeView`/`WebAgentRuntimeView` 三个视图在 `apps/web/src/` 内无任何 `import` 引用（grep 已核实），疑似统一重构进 `AiRuntimeChatView` 后的旧实现，建议清理确认。

> 与本文档配套的 `docs/安全审计报告.md` 记录了上述设计在安全维度的具体风险（token 存储、扩展宽 host 权限、Nginx 缺安全头、DB `useSSL=false` 等）与修复建议。
